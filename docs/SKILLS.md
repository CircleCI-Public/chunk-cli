# Skills

Skills are instruction files for AI coding agents. Installing them teaches agents how to use `smelt` commands — sidecar setup and the remote validation dev loop, plus test gap analysis, CI debugging, and code review — through natural-language triggers.

Skills below are listed alphabetically. If you are setting up for the first time, start with [`smelt-sidecar-setup`](#smelt-sidecar-setup), then use [`smelt-sidecar`](#smelt-sidecar) for the day-to-day loop.

## Installing skills

```bash
smelt skill install     # install or update all skills
smelt skill list        # show installation status per agent
```

Skills are installed into the configuration directories of whichever agents are present on your machine:

| Agent | Install path |
|---|---|
| Claude Code (CLI / desktop) | `~/.claude/skills/` |
| Cursor | `~/.cursor/skills/` |
| Codex | `~/.codex/skills/` |

`smelt skill list` shows the status for each skill on each agent:

- **current** — installed and up to date
- **outdated** — installed but a newer version is available; re-run `smelt skill install`
- **missing** — not installed; run `smelt skill install`
- **n/a** — agent not found on this machine

Skills are versioned. Run `smelt skill install` again after upgrading `smelt` to keep them in sync.

## Available skills

### smelt-review

**Trigger phrases**: "review my changes", "smelt review", "review my diff", "review this PR", "review PR #123", "review PR `<url>`"

Applies your team's generated review standards to the current diff. The review runs in an isolated subagent so prior conversation context does not influence findings.

**Prerequisites**:
- `.smelt/context/review-prompt.md` must exist (generated by `smelt build-prompt`)
- For PR reviews: `gh` CLI must be installed and authenticated

**What it does**:

1. Determines the diff scope — PR diff via `gh`, staged changes, or uncommitted changes against main
2. Loads `.smelt/context/review-prompt.md` from the PR branch (or local fallback)
3. Runs a two-pass review in a subagent:
   - Pass 1: comprehensive scan against all review standards
   - Pass 2: validate each finding with a concrete failure scenario; filter to Critical/High issues; cap at 10 comments
4. Returns filtered findings with file, line number, impact rating, and suggested fix

**Example output**:

```
## Review Summary

Files reviewed: 4
Issues identified: 2

### 1. Missing error check on file write
`internal/store/write.go:42` | **High**

`os.WriteFile` can fail silently if the destination is read-only or the disk
is full. The error return is discarded here. Downstream code assumes the file
exists and will panic on next read.

Suggested fix: check and return the error.
```

If no issues survive filtering, the skill reports "No significant issues identified."

### smelt-sidecar

**Trigger phrases**: "validate on the sidecar", "run tests on the sidecar", "sync to sidecar", "sidecar dev loop", "validate remotely", "run smarter testing doctor", "diagnose smarter testing"

Smart entry point for all sidecar workflows. Probes your current state (CLI installed, auth configured, active sidecar, snapshot configured) and uses interactive questions to route you to the right flow: first-time setup, dev loop, debugging, test-suite scaffolding, or snapshot management.

**What it does**:

1. Runs read-only state probes (`smelt --version`, `smelt auth status`, config, `smelt sidecar current`)
2. Asks what you want to do, with options tailored to your current state
3. Routes to the matching flow:
   - No sidecar, no snapshot → delegates to `smelt-sidecar-setup` for first-time onboarding
   - Snapshot configured, no active sidecar → launches from snapshot, then starts the dev loop
   - Active sidecar → sync → validate loop, with options for debug, scaffolding, or snapshot management

**The dev loop in practice**:

```
You: validate on the sidecar
Agent: [probes state — active sidecar found]
       What would you like to do?
       > Sync and validate (dev loop) ← chosen
       syncing local changes...
       running smelt validate...
       ✗ test failed: internal/store_test.go:88: assertion failed
       Fixing the issue...
       syncing again...
       running smelt validate...
       ✓ all validations passed
```

**Parallel sessions**: When multiple Claude sessions are open in the same repo, each session automatically targets its own sidecar pool — two sessions never sync into the same remote workspace. State is keyed by session and branch and stored in `XDG_DATA_HOME` (see Architecture docs); the session comes from the Stop hook payload, or from `CLAUDE_CODE_SESSION_ID` for commands the agent runs itself. No manual configuration is needed; set `SMELT_SESSION_ID` to pin the identity by hand (for an agent other than Claude Code, say).

### smelt-sidecar-setup

**Trigger phrases**: "set up smelt sidecar", "onboard to smelt", "first time sidecar", "configure sidecar from scratch", "walk me through sidecar setup", "I've never used a smelt sidecar before"

Interactive onboarding wizard for setting up a sidecar from scratch. Also invoked automatically by `smelt-sidecar` when no sidecar or snapshot is configured.

**Prerequisites**:
- `smelt` CLI installed
- CircleCI auth (`smelt auth login`, or `smelt auth set circleci` for token auth)

**What it does** (8 guided stages):

1. **Prerequisites** — checks `smelt --version` and `smelt auth status`; explains each credential and what it's needed for
2. **OrgID** — confirms your CircleCI org ID is set; explains how to find it in the dashboard if needed
3. **Sidecar name** — asks whether to auto-generate a name or choose one
4. **Create + sync** — runs `smelt sidecar create` and `smelt sidecar sync`; explains what sync does
5. **Install dependencies** — auto-detect with `smelt sidecar setup`, custom commands, or skip
6. **Smarter Testing** — asks whether to install `circleci-testsuite` on the sidecar
7. **Validate** — runs `smelt validate` and loops on failures until it passes
8. **Snapshot** — creates a reusable snapshot, persists the image ID in config, launches a clean sidecar from it, and re-verifies

Ends with a summary of what was configured and instructions for using `/smelt-sidecar` for the dev loop going forward.

### smelt-validate-config

**Trigger phrases**: "smelt keeps making me wait", "stop smelt blocking every turn", "run my tests in the background", "configure background validation", "always validate my migrations", "change the async validate threshold"

Reads and sets the `asyncValidate*` keys in `.smelt/config.json` – the ones that
decide whether the agent waits for `smelt validate` or is released and told the
answer on its next turn. Nothing it sets changes *whether* a change is
validated; only who waits.

**What it does**:

1. **Asks what you want** – to wait less often, to always wait, or to always wait for particular paths
2. **Looks at the repo** rather than guessing, using `git diff --name-only` and the project's file types
3. **Sets the narrowest key that does it** via `smelt config set`, which validates the value first: `asyncValidate`, `asyncValidateMaxLines`, `asyncValidateInert`, `asyncValidateBlocking`, `asyncValidateWorktree`
4. **Says what changed in one line** – which key, what value, and whether you now wait more or less

It will not put source extensions (`.go`, `.ts`, `.py`) in the inert list, and
it asks before setting `asyncValidateWorktree`, which reports environment
failures as code failures in a project whose checks need gitignored files.

See [HOOKS.md](HOOKS.md#background-validation) for what each key means.

### smelt-testing-gaps

**Trigger phrases**: "find testing gaps", "smelt testing-gaps", "mutation test", "mutate this code", "test mutation coverage", "find surviving mutants"

Runs a four-stage mutation testing process to find undertested code paths.

**What it does**:

1. **Discovery** — identifies mutation candidates in changed code
2. **Validation** — triages candidates locally, then runs the survivors on a temporary sidecar pool via `smelt validate variants`
3. **Production cross-reference** — checks whether survivors touch production code paths
4. **Risk assessment** — reports high-risk survivors with recommended tests

Mutants never leave your machine as VCS artifacts: each one is carried as a patch and applied on a sidecar that is deleted afterwards. No branches are pushed and no pull requests are opened.

### debug-ci-failures

**Trigger phrases**: "debug CI", "why is CI failing", "fix CI failures", "find flaky tests", "what broke in CI", "check CircleCI"

Analyzes CircleCI pipeline failures and identifies flaky tests.

**What it does**:

1. Detects the project and current pipeline
2. Fetches build failure logs
3. Analyzes test results for patterns
4. Distinguishes genuine failures from flaky tests
5. Reports root cause with remediation steps

## Keeping skills up to date

Skills are bundled into the `smelt` binary. When you upgrade `smelt`, run `smelt skill install` again to push the updated skill files to your agents.

```bash
smelt upgrade           # update smelt itself
smelt skill install     # update skill files in agent dirs
```

## Using skills without an agent

Skills are markdown files the agent reads. You can read them directly for reference:

```bash
# Claude Code skill files after install
cat ~/.claude/skills/smelt-review.md
cat ~/.claude/skills/smelt-sidecar.md
```

## Troubleshooting

**`smelt skill list` shows "n/a" for all agents**

The agent configuration directories were not found. Make sure the agent is installed. Claude Code creates `~/.claude/` on first launch.

**Skills show "outdated"**

Run `smelt skill install` to update them.

**Agent doesn't respond to skill triggers**

Confirm the skill is installed (`smelt skill list`). Some agents require a restart after new skill files are added. Check the agent's documentation for how it loads skill files.

**`smelt-review` says "review-prompt.md not found"**

The team review prompt hasn't been generated yet. Run `smelt build-prompt` to create it, then commit `.smelt/context/review-prompt.md` so all team members have it.
